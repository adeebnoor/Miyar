# Pages publication after release checks — 6.3.1

The release test workflow must finish before Pages waits for a matching live API. Previously, its deployment job waited for Render while Render's `checksPass` setting waited for that same test/deploy workflow to finish. Pages publication now runs in a separate completion-triggered workflow.

1. `.github/workflows/pages.yml` retains the name **Test and deploy Miyar to GitHub Pages**. Its server, UI and real-browser jobs run as before, including PostgreSQL, dependency audit, real semantic resource measurement and browser/link acceptance. `release-checks` explicitly requires all three results to be `success`; it never calls the live API or publishes Pages.
2. `.github/workflows/publish-pages.yml` starts only after that named workflow completes. Its deployment job accepts only a successful run from this repository's `main` branch whose original event was `push` or `workflow_dispatch`. Pull-request and fork runs cannot publish. The publisher has no standalone manual dispatch trigger. A rerun retains its already-successful triggering test run and SHA; a new source commit must pass all test gates again.
3. The publisher checks out `workflow_run.head_sha`, rather than the default branch's latest commit, then builds that tested release. The existing `check-live-release.py` identity check and `check-live-services.py` export/protected-response checks still run before configuring/uploading/deploying Pages. Release mismatch or a failed service check blocks publication.
4. The publisher has its own concurrency group and cancels a superseded publisher. Its workflow-wide permissions are empty; the only publishing job grants the existing minimum `contents: read`, `pages: write` and `id-token: write`. Checkout does not retain credentials. No test artifacts from pull requests are downloaded or executed.

Render's `autoDeployTrigger: checksPass`, hosting configuration, authentication settings and API release checks remain unchanged. This change neither manually triggers Render nor asserts that any live deployment has completed. Verify both completed test and publishing runs, and matching API/Pages release identities, after the files reach `main`.

GitHub requires a `workflow_run` workflow to exist on the default branch. It also notes that its default SHA is the default-branch commit, that it can access write tokens, and that running untrusted code through it can expose privileges or poison caches. These are why the publisher checks the original event/repository/branch and uses the exact tested SHA. See the [official workflow_run documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).

## Render all-checks ordering limit

Render waits for all detected GitHub checks, and `workflow_run` can itself register a publishing check against the same default-branch SHA. The split removes the in-workflow dependency but does not guarantee automatic Render ordering. After every test gate succeeds, inspect the Render deploy list. If the publisher is waiting for the API and no deploy exists for that SHA, an authorized maintainer must deploy the exact tested commit through Render; do not disable CI checks or the API identity gate. If the publisher has timed out, rerun that publisher only after the exact API release is live. Its preserved triggering run still identifies the successfully tested commit.

See [Render CI deployment semantics](https://render.com/docs/deploys) and the [commit-specific deploy API](https://api-docs.render.com/reference/create-deploy). This recovery changes neither hosting tier, region, access nor authentication.
